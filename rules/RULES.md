# 코드 규칙

이 저장소의 모든 TypeScript 코드는 아래 규칙을 따릅니다. 테스트 코드에도 똑같이 적용합니다. 작성 가이드의 주석, 이력, 티켓 만들기, 티켓 고치기, 티켓의 상태, 티켓 읽기 항목은 `apps/`, `packages/`, `scripts/` 아래의 JavaScript 파일과 주석을 쓸 수 있는 설정 파일에도 적용합니다.

규칙에 어긋난 코드와 규칙에 맞는 코드의 짝은 같은 폴더의 `EXAMPLES.md` 에 있습니다. 규칙을 코드로 옮기는 방법이 확실하지 않을 때 읽습니다.

## 핵심 원칙

- 중복 제거: 코드가 반복되지 않도록 공통 로직을 묶습니다.
- 단일 책임: 클래스나 함수는 한 가지 일만 해야 합니다.
- 의도 드러내기: 코드가 수행하는 일을 명시하고, 작성자의 의도가 숨겨지지 않게 합니다.
- 단순함: 군더더기 없이 직접적이고 단순하게 작성합니다.

## 작성 가이드

- 의미 있는 이름: 변수나 함수 이름은 길더라도 서술적이고 명확한 단어를 사용합니다.
- 작은 함수: 함수의 인자는 3개 이하로 유지합니다. 프레임워크가 인자의 수와 순서를 정한 함수만 예외입니다. 인자가 3개를 넘는 함수는 하는 일을 나눕니다. 인자의 수를 줄이려고 인자들을 새 객체 타입으로 묶지 않습니다. 받은 값을 그대로 객체로 돌려주는 함수는 만들지 않고, 값이 필요한 자리에 객체를 직접 적습니다. 다른 모듈이 객체를 직접 적어야 하는 타입은 그 타입을 선언한 모듈이 내보냅니다.
- 작은 단위: 코드는 읽기 좋은 잘 쓴 글처럼 직관적이어야 합니다.
- 삼항 연산자: 삼항 연산자는 두 값 가운데 하나를 고를 때만 씁니다. 삼항 연산자 안에 삼항 연산자를 다시 쓰지 않습니다. 조건이 둘 이상이면 함수로 빼고, `if` 문 안에서 바로 `return` 합니다.
- 가져오기 경로: 모듈을 가져올 때 `./` 나 `../` 로 시작하는 상대 경로를 쓰지 않습니다. 앱이나 패키지의 이름으로 시작하는 경로를 씁니다. 저장소의 패키지 이름이 `@acme/` 로 시작하면 `@acme/<폴더 이름>/` 뒤에 그 폴더 안의 경로를 적습니다. `apps/web/workers/handler.ts` 는 `@acme/web/workers/handler` 로 가져옵니다. 이 대응은 저장소 루트에 있는 `tsconfig.base.json` 의 `paths` 한 곳에 선언합니다. 다른 패키지의 파일은 그 패키지가 `package.json` 의 `exports` 로 내보낸 경로로만 가져옵니다.
- 스프레드: 스프레드(`...`)는 쓸 수 있습니다. 다음 네 경우에는 쓰지 않습니다.
  - 반복문 안에서 객체나 배열을 스프레드로 다시 만들어 값을 누적하지 않습니다. 걸리는 시간이 반복 횟수의 제곱에 비례합니다. 속성에 대입하거나 `push` 를 쓰고, 키로 값을 찾는 누적에는 `Map` 의 `set` 을 씁니다.
  - 스프레드로 복사한 객체 안의 객체와 배열은 원본과 같은 값입니다. 복사본 안의 객체와 배열을 고치지 않습니다.
  - 클래스의 인스턴스, `Date`, `Map`, `Set` 을 객체 스프레드로 복사하지 않습니다. 메서드와 getter 가 복사되지 않습니다.
  - 객체 스프레드는 타입에 선언하지 않은 속성도 복사합니다. 덮어써도 되는 속성이 정해져 있는 자리와, 응답이나 로그로 프로그램 밖에 내보내는 객체를 만드는 자리에서는 스프레드를 쓰지 않고 속성의 이름을 하나씩 적습니다.
- 주석: 주석은 코드로 표현할 수 없는 이유를 적을 때만 씁니다. 함수의 이름, 인자의 타입, 반환 타입만 보고 알 수 있는 내용은 주석으로 적지 않습니다. 이름만 보고 알 수 없는 뜻은 주석으로 적지 않고 이름에 담습니다. 이름을 바꿀 수 없는 값은 그 값을 읽는 자리에서 새 이름으로 옮깁니다.
- 이력: 코드가 언제, 왜 바뀌었는지는 주석에 적지 않습니다. 저장소 루트의 `.decisions/` 폴더에 티켓 파일을 만들어 적고, 코드의 주석에는 `// .decisions/<식별자>` 형식으로 티켓의 식별자만 적습니다. 새로 쓴 코드에서 선택한 이유를 남길 때는, 코드만 읽어서는 알 수 없는 이유는 주석으로 적고 날짜, 선택하지 않은 방법, 측정값은 티켓에 적습니다.
- 티켓 만들기: 티켓의 내용을 `.decisions/` 폴더의 파일에 먼저 적습니다. 첫 줄은 `# ` 뒤에 바뀐 내용을 한 줄로 적은 제목이고, 본문에는 코드가 언제, 왜 바뀌었는지를 적습니다. 내용을 적은 파일에 `git hash-object <파일 경로>` 를 실행하면 40자리 해시가 출력됩니다. 해시의 앞 8자리가 티켓의 식별자입니다. 파일의 이름을 `<식별자>.md` 로 바꿉니다.
- 티켓 고치기: 커밋하는 티켓 파일의 이름은 파일 내용의 해시 앞 8자리와 같아야 합니다. `origin/develop` 브랜치에 있는 티켓은 내용이 틀렸거나 코드와 맞지 않게 되어도 고치지 않습니다. 새 티켓을 만들어 본문에 이전 티켓의 식별자를 적고, 코드의 주석에 적힌 식별자를 새 티켓의 식별자로 바꿉니다. `origin/develop` 브랜치에 아직 없는 티켓은 내용을 고친 뒤 식별자를 다시 구해 파일의 이름과 코드의 주석을 바꿉니다.
- 티켓의 상태: 티켓의 상태는 두 가지이고, 티켓 파일이 놓인 폴더가 상태를 나타냅니다. 유효한 티켓은 식별자가 코드의 주석에 적혀 있는 티켓이고, `.decisions/` 바로 아래에 둡니다. 효력을 잃은 티켓은 식별자가 코드의 어느 주석에도 적혀 있지 않은 티켓이고, `git mv` 로 `.decisions/.retired/` 폴더로 옮깁니다.
- 티켓 읽기: 코드의 주석에 식별자가 적힌 티켓만 `.decisions/<식별자>.md` 경로로 읽습니다. 효력을 잃은 티켓은 유효한 티켓의 본문이나 `origin/develop` 브랜치의 이전 커밋에 있는 코드에 식별자가 적혀 있을 때 `.decisions/.retired/<식별자>.md` 경로로 읽습니다.

## 타입

- 타입 단언(`값 as 타입`)과 non-null 단언(`값!`)을 쓰지 않습니다. `as const` 는 예외입니다.
- `any` 타입을 쓰지 않습니다.
- 함수의 반환 타입과, 초기값이 있는 변수의 타입은 적지 않습니다. TypeScript 가 추론합니다. 값이 특정 타입에 맞는지 확인할 때는 `satisfies` 를 씁니다. 함수가 돌려주는 값이 특정 타입에 맞는지 확인할 때는 `return` 식에 `satisfies` 를 붙입니다. 이름을 붙여 선언한 타입에 맞아야 하는 객체를 변수에 담거나 `return` 할 때 `satisfies` 를 붙입니다. 함수의 인자로 바로 넘기는 값에는 붙이지 않습니다.
- 근원 타입은 다른 타입으로부터 만들지 않은 타입입니다. 근원 타입은 이름을 붙여 한 번만 선언합니다. 구조가 같은 타입을 두 번 선언하지 않습니다. 함수 하나의 인자에서만 쓰는 객체 타입은 인자 자리에 직접 적어도 됩니다. 두 곳 이상에서 쓰는 객체 타입에는 이름을 붙입니다.
- 값이 없을 수 있는 속성과 변수에만 `?` 와 `| undefined` 를 씁니다.
- `enum` 을 쓰지 않습니다.
- 가질 수 있는 값이 정해진 자리에는 `string` 이나 `number` 를 쓰지 않고, 그 값을 모두 나열한 리터럴 유니온 타입을 씁니다. 값의 목록은 `as const` 로 한 번만 적고, 유니온 타입은 그 목록에 `typeof` 를 적용해 만듭니다. 실행 중에 값의 목록을 읽는 코드가 없으면 `as const` 목록을 만들지 않고 리터럴 유니온 타입만 선언합니다.
- 프로그램 밖에서 들어온 값은 zod 스키마로 검증한 다음에 씁니다. HTTP 요청, 외부 API 의 응답, 환경 변수, 파일의 내용, `JSON.parse` 의 결과가 프로그램 밖에서 들어온 값입니다. 검증한 값의 타입은 따로 선언하지 않고 `z.infer` 로 스키마에서 얻습니다. `transform` 이 붙은 스키마에서 `z.infer` 는 변환한 뒤의 타입입니다. 변환하기 전의 타입은 `z.input` 으로 얻습니다.
- 이미 있는 타입이나 값으로 표현할 수 있는 타입은 직접 선언하지 않고 그 타입이나 값으로부터 만듭니다. 만들 때는 generics, `keyof`, `typeof`, indexed access 타입, conditional 타입, mapped 타입, template literal 타입을 씁니다. `string`, `number`, `boolean` 하나로 적는 속성의 타입은 그대로 적습니다. 객체 타입, 유니온 타입, 리터럴 타입은 이미 있는 타입에서 가져옵니다.
- TypeScript 가 전역으로 제공하는 유틸리티 타입으로 만들 수 있는 타입은 유틸리티 타입으로 만듭니다.
- 다음 네 가지 타입은 컴파일 시간을 늘리므로 정해진 방식으로 씁니다.
  - 객체 타입을 합칠 때는 교차 타입(`A & B`)을 쓰지 않고, `interface` 가 합칠 타입들을 `extends` 하게 합니다.
  - 객체 타입 13개 이상을 한 유니온으로 묶지 않습니다. 공통 속성을 가진 기반 `interface` 를 선언하고, 각 객체 타입이 기반 `interface` 를 `extends` 하게 합니다.
  - conditional 타입을 함수의 인자 타입이나 반환 타입 자리에 직접 쓰지 않습니다. 타입 별칭으로 선언하고 별칭의 이름을 씁니다.
  - template literal 타입의 보간 자리에 유니온을 넣으면 각 유니온의 멤버 수를 곱한 개수만큼 문자열 리터럴 타입이 만들어지고, 이 개수가 100,000 이상이면 컴파일이 실패합니다. 유니온을 두 개 이상 넣을 때는 이 개수를 먼저 계산합니다.
- 타입 검사에 걸리는 시간은 `tsc --extendedDiagnostics` 가 출력하는 `Check time` 과 `Instantiations` 로 확인합니다.
